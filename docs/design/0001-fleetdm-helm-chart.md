# DESIGN 0001: FleetDM Helm Chart

**Status:** Implemented
**Author:** Donald Gifford
**Date:** 2026-03-15

## Overview

A first-party Helm chart for FleetDM that replaces the upstream chart's broken Bitnami
subcharts with a clean PXC-backed MySQL integration, optional Valkey cache, and Gateway
API HTTPRoute ingress. The chart follows the existingSecret pattern throughout and is
designed for ArgoCD + kustomize deployment.

## Goals and Non-Goals

### Goals

- Replace broken upstream FleetDM chart with a production-ready alternative
- Use Percona XtraDB Cluster (PXC) CR for MySQL instead of Bitnami subcharts
- Support externally managed secrets (1Password Connect, External Secrets Operator)
- Use Gateway API HTTPRoute instead of classic Ingress
- Full test coverage: helm-unittest, helm test hooks, chart-testing CI values
- Automated appVersion tracking via Renovate/Dependabot

### Non-Goals

- Installing the PXC operator (deployed separately, must be watching the namespace)
- Defaulting to classic `Ingress` (Gateway API `HTTPRoute` is the primary path; `Ingress`
  is supported but disabled by default)
- Managing Fleet Premium licensing (only mounts the license key secret if configured)
- Running Fleet with TLS termination in the application (TLS terminates at the gateway)

## Background

The upstream FleetDM Helm chart depends on Bitnami MySQL and Redis subcharts that
frequently break on version bumps and carry unnecessary complexity. FleetDM requires
MySQL and an optional Redis-compatible cache. This chart uses a `PerconaXtraDBCluster` CR
(managed by the PXC operator deployed as a separate application) and an optional
first-party Valkey StatefulSet.

## Detailed Design

### Key Design Decisions

- **No PXC operator installation.** The chart only creates a `PerconaXtraDBCluster` CR.
  The operator must be deployed separately and watching the target namespace.
- **Cache disabled by default.** Users bring their own Redis-compatible instance or enable
  the bundled Valkey deployment.
- **existingSecret pattern.** The chart generates random credentials by default, but any
  secret section can be overridden with an external secret name. Generated secrets use
  `helm.sh/resource-policy: keep` to survive upgrades.
- **Gateway API HTTPRoute as default.** `HTTPRoute` is enabled by default. Classic
  `Ingress` is also supported via a separate template but disabled by default. `parentRefs`
  are user-provided values with no gateway-specific defaults.
- **Version management by Renovate/Dependabot.** `appVersion` in `Chart.yaml` tracks the
  Fleet release tag. Chart version bumps independently.

### Prerequisites and Dependencies

| Dependency | Required Version | How to Validate |
|------------|-----------------|-----------------|
| Kubernetes | 1.25+ | `kubectl version` |
| Helm | 3.10+ | `helm version` |
| PXC Operator | 1.13+ (when `pxc.enabled: true`) | `kubectl get deployment percona-xtradb-cluster-operator -n <namespace>` |
| Gateway API CRDs | v1 (when `httpRoute.enabled: true`) | `kubectl get crd httproutes.gateway.networking.k8s.io` |
| cert-manager | v1.12+ (when `httpRoute.certManager.enabled: true`) | `kubectl get crd certificates.cert-manager.io` |

The PXC operator must be deployed and watching the target namespace **before** installing
this chart with `pxc.enabled: true`. If the operator is not present, the
`PerconaXtraDBCluster` CR will be created but remain in a pending state with no controller
to reconcile it. Validate with:

```sh
kubectl get pods -n <namespace> -l app.kubernetes.io/name=percona-xtradb-cluster-operator
```

### Helper Functions (`_helpers.tpl`)

Beyond standard name/label helpers:

- `fleetdm.mysqlSecretName` — returns `existingSecret` if set, otherwise chart-generated
  secret name
- `fleetdm.redisSecretName` — same pattern for Redis/Valkey credentials
- `fleetdm.pxcSecretName` — same pattern for PXC operator credentials
- `fleetdm.mysqlAddress` — returns `database.address` if set; derives
  `<clusterName>-haproxy.<namespace>:3306` when `pxc.enabled`; otherwise calls `fail` with
  message: `"database.address is required when pxc.enabled is false"`
- `fleetdm.redisAddress` — returns `cache.address` if set; derives from Valkey service
  when `valkey.enabled`; otherwise calls `fail` with message:
  `"cache.address is required when valkey.enabled is false"`
- `fleetdm.image` — combines `image.repository` and `image.tag`, falling back to
  `.Chart.AppVersion` when tag is empty

Helper `fail` calls produce a clear `helm template` / `helm install` error that tells the
user exactly which value to set, rather than rendering an invalid manifest.

### Secrets

Three conditional secrets, each skipped when its corresponding `existingSecret` is set:

1. **MySQL secret** — `database.existingSecret` controls. Contains the password key.
2. **PXC credentials secret** — `pxc.existingSecret` controls. Must contain keys: `root`,
   `xtrabackup`, `monitor`, `clustercheck`, `proxyadmin`, `pmmserver`, `operator`.
3. **Redis/Valkey secret** — only rendered when `cache.usePassword: true` and
   `cache.existingSecret` is not set.

All generated secrets use `helm.sh/resource-policy: keep` to survive upgrades.

**existingSecret example with External Secrets Operator:**

```yaml
# ExternalSecret CR (deployed separately, before the chart)
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: fleet-mysql-credentials
spec:
  secretStoreRef:
    name: 1password-connect
    kind: ClusterSecretStore
  target:
    name: fleet-mysql-credentials
  data:
    - secretKey: mysql-password
      remoteRef:
        key: fleet-mysql
        property: password
---
# Chart values referencing the ExternalSecret's target
database:
  existingSecret: fleet-mysql-credentials
  passwordKey: mysql-password
```

### PXC Cluster CR (`pxc-cluster.yaml`)

Gated behind `pxc.enabled`. The `secretsName` field references the output of
`fleetdm.pxcSecretName`. Includes ArgoCD annotation for server-side apply:

```yaml
annotations:
  argocd.argoproj.io/sync-options: "ServerSideApply=true"
```

### Deployment

Fleet env vars wired via helper functions:

- `FLEET_MYSQL_ADDRESS` — from `fleetdm.mysqlAddress`
- `FLEET_MYSQL_PASSWORD` — secretKeyRef from `fleetdm.mysqlSecretName`
- `FLEET_REDIS_ADDRESS` — from `fleetdm.redisAddress`
- `FLEET_REDIS_PASSWORD` — conditional on `cache.usePassword`
- `FLEET_LICENSE_KEY` — conditional on `fleet.license.secretName`

Mounts a `tmp` emptyDir to satisfy `readOnlyRootFilesystem: true`.

### HTTPRoute (`httproute.yaml`)

Renders two documents when both flags are enabled:

1. `cert-manager.io/v1 Certificate` — only when `httpRoute.certManager.enabled` is true
2. `gateway.networking.k8s.io/v1 HTTPRoute` — always when `httpRoute.enabled` is true.
   `parentRefs` taken verbatim from values.

### Ingress (`ingress.yaml`)

Classic `networking.k8s.io/v1 Ingress` resource, disabled by default. Provided for
environments not yet on Gateway API. Gated behind `ingress.enabled`. Supports standard
annotations (e.g., `nginx.ingress.kubernetes.io/*`, cert-manager `cluster-issuer`), TLS
configuration, and custom paths. Only one of `httpRoute.enabled` or `ingress.enabled`
should be set — the chart does not validate mutual exclusivity but the README documents it.

### Valkey (`valkey.yaml`)

StatefulSet + headless Service when `valkey.enabled: true`. Persistence is optional,
defaults to emptyDir. When `cache.usePassword: true`, passes the password via env and
starts Valkey with `--requirepass`.

### Minimum Resource Requirements

| Component | CPU Request | Memory Request | Notes |
|-----------|------------|----------------|-------|
| Fleet | 250m | 256Mi | Single replica baseline; scale via HPA |
| PXC node (x3) | 600m | 1Gi | Per node; 3-node cluster = 1.8 CPU / 3Gi total |
| PXC HAProxy (x2) | 100m | 128Mi | Per instance |
| Valkey | 100m | 128Mi | Single replica; increase for large fleets |

A minimal production deployment (Fleet + 3-node PXC + HAProxy) requires approximately
**3 CPU / 4Gi memory** in requests across all components.

## API / Interface Changes

### `values.yaml` Key Sections

**Fleet app config:** `replicaCount`, `image` (repository/tag/pullPolicy), `fleet.tls`,
`fleet.logging`, `fleet.serverURL`, `fleet.license`, `fleet.autoApplySQLMigrations`

**Database (MySQL via PXC HAProxy):** `database.address` (auto-derived from PXC when
empty), `database.name`, `database.username`, `database.existingSecret`,
`database.passwordKey`, connection pool settings

**Cache:** `cache.address` (auto-derived from Valkey when empty), `cache.usePassword`,
`cache.existingSecret`, `cache.passwordKey`

**PXC cluster:** `pxc.enabled`, `pxc.clusterName`, `pxc.size` (must be odd: 1,3,5,7),
`pxc.image`, `pxc.resources`, `pxc.storage`, `pxc.haproxy`, `pxc.existingSecret`,
`pxc.backup`

**Valkey:** `valkey.enabled` (disabled by default), `valkey.image`, `valkey.replicaCount`,
`valkey.resources`, `valkey.persistence`, `valkey.service.port`

**HTTPRoute (default):** `httpRoute.enabled` (true by default), `httpRoute.hostname`,
`httpRoute.parentRefs`, `httpRoute.certManager` (enabled, clusterIssuer, certificateName)

**Ingress (alternative):** `ingress.enabled` (false by default), `ingress.className`,
`ingress.annotations`, `ingress.hosts`, `ingress.tls`

**Standard Kubernetes:** `serviceAccount`, `service`, `resources`, `autoscaling`,
`podDisruptionBudget`, `nodeSelector`, `tolerations`, `affinity`

### `values.schema.json` Constraints

- `database.name`, `database.username`, `database.passwordKey` — required non-empty
  strings
- `pxc.size` — enum of `[1, 3, 5, 7]` (odd values only for Galera quorum)
- `autoscaling.targetCPUUtilizationPercentage` — integer 1-100
- `valkey.replicaCount` — minimum 1

## Data Model

No persistent data owned by the chart itself. The PXC CR manages MySQL storage via PVCs
configured through `pxc.storage.size` and `pxc.storage.storageClassName`. Valkey
persistence is optional and uses a PVC when enabled.

## Testing Strategy

### Helm Test Hooks (`templates/tests/`)

- **test-mysql-connection.yaml** — `mysql:8.0` pod runs `SELECT 1` against PXC HAProxy
- **test-valkey-connection.yaml** — `valkey/valkey` pod runs `PING` (only when cache is
  configured)
- **test-fleet-health.yaml** — `curlimages/curl` hits `/healthz` on Fleet service
  (hook-weight 5, runs after connection tests). This validates that Fleet has started,
  connected to MySQL, run migrations (if `autoApplySQLMigrations: true`), and is serving
  requests.

### Unit Tests (`tests/`, helm-unittest)

10 test suites covering all templates:

- **deployment_test.yaml** — replicas, image tag, env vars for all secret/address
  combinations, autoscaling interaction, security context, emptyDir mount
- **secret_test.yaml** — conditional rendering for MySQL/PXC/Redis secrets, existingSecret
  skip, resource-policy keep annotation
- **pxc_cluster_test.yaml** — enabled/disabled rendering, cluster name, size, secret name
  derivation, haproxy defaults, backup toggle, ArgoCD SSA annotation
- **httproute_test.yaml** — enabled/disabled rendering, parentRefs guard, Certificate +
  HTTPRoute combo, hostname, parentRefs
- **ingress_test.yaml** — enabled/disabled, className, annotations, TLS config
- **hpa_test.yaml** — enabled/disabled rendering, min/max replicas, CPU target
- **pdb_test.yaml** — enabled/disabled rendering, minAvailable
- **service_test.yaml** — service type, port
- **serviceaccount_test.yaml** — create/skip, annotations, automount disabled
- **valkey_test.yaml** — enabled/disabled, emptyDir/PVC persistence, requirepass toggle

### Chart Testing CI Values (`ci/`)

- **default-values.yaml** — PXC and Valkey disabled, stub database/cache addresses.
  Resources render and apply cleanly in Kind without the PXC operator.
- **ha-values.yaml** — HPA, PDB, Valkey, and HTTPRoute enabled to exercise all code paths.

### Integration Testing Gaps

The `ct install` tests with stub addresses verify that all resources render and apply, but
do not test the full Fleet startup sequence (MySQL connection, schema migration, HTTP
readiness). Full end-to-end testing requires the PXC operator in the Kind cluster, which
adds CI complexity. For initial release, full integration is validated manually via
`helm test` against a real cluster. A future CI enhancement could add a dedicated
integration job that installs the PXC operator in Kind.

## Migration / Rollout Plan

### Migrating from the Upstream FleetDM Chart

For users migrating from the upstream FleetDM Helm chart:

1. **Data is in MySQL, not the chart.** The upstream chart's Bitnami MySQL subchart stores
   data in PVCs. Before switching, back up the Fleet database with `mysqldump`.
2. **Deploy PXC operator and cluster first.** Install the PXC operator and create the
   cluster (this chart handles the CR). Restore the database dump into the new PXC cluster.
3. **Map existing secrets.** If using the upstream chart's auto-generated secrets, extract
   the MySQL password and either create a matching secret or use `existingSecret` to
   reference it.
4. **Install this chart with `fleet.autoApplySQLMigrations: true`.** Fleet will detect the
   existing schema and apply any pending migrations on startup.
5. **DNS cutover.** Update the HTTPRoute hostname or DNS records to point at the new
   deployment.

**There is no in-place upgrade path** from the upstream chart to this chart. The resource
names, label selectors, and subchart dependencies are different. This is a fresh install
with a data migration.

### ArgoCD Integration

- **ignoreDifferences** on the FleetDM Application to suppress PXC operator status field
  drift:

  ```yaml
  ignoreDifferences:
    - group: pxc.percona.com
      kind: PerconaXtraDBCluster
      jsonPointers:
        - /status
  ```

- **Server-side apply** via annotation on the PXC CR so the operator can own its own
  fields without conflicting with ArgoCD's three-way merge.
- **Secret lifecycle** — generated secrets use `helm.sh/resource-policy: keep`. When using
  `existingSecret` (1Password Connect), the chart skips creating secrets entirely.

## Resolved Questions

- **helm-diff in CI:** Local-only tool. Adding it to CI requires live cluster credentials
  in the workflow, which is unnecessary complexity. Developers run `helm diff upgrade`
  locally before merging to reason about what ArgoCD will apply.
- **Classic Ingress support:** Support both. Gateway API `HTTPRoute` is the default and
  enabled by default. Classic `Ingress` is also supported via an `ingress.yaml` template
  but disabled by default. This broadens compatibility for users not yet on Gateway API.
- **Minimum Fleet version:** Pin to the newest available version at chart creation time.
  No backward-compatibility conditional logic for older Fleet versions. Users on older
  Fleet versions should use the upstream chart or pin `image.tag` explicitly.
- **PXC operator version compatibility:** Document the minimum tested operator version in
  the chart README and prerequisites table. The CR schema is relatively stable within a
  major version, so pinning a minimum (e.g., 1.13+) is sufficient.
- **Full integration CI job:** Too heavy for PR CI. The PXC operator is specific to this
  chart's MySQL backend choice, not a general concern. Full e2e validation (PXC operator +
  `helm test`) is done manually or in a dedicated staging environment, not in PR CI.
- **ArgoCD status drift beyond PXC:** No known drift issues with the Fleet Deployment or
  other resources at this time. Only the PXC CR requires `ignoreDifferences` for operator
  status fields. Revisit if drift is observed after initial deployment.
